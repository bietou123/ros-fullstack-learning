# S4-01 · CAN 物理层与帧结构

> 验证状态：概念课，命令为通用 Linux/SocketCAN 工具命令，**本机未连接真实 CAN 设备，未实测**。

## 1. 现场类比

ROS 话题是「软件内部的语言」，CAN 是「车上真正跑的电信号」。一段控制指令从 ROS 走到液压阀，中间一定经过 CAN 帧。

现场排查「指令发了但车不动」时，如果不了解 CAN 帧长什么样，就只能在软件层猜。**能读懂一帧，就能判断问题在上游算法还是下游执行。**

## 2. 核心概念

### 2.1 物理层要点

| 项目 | 内容 | 现场意义 |
|---|---|---|
| 总线 | 双绞线 CAN_H / CAN_L，差分信号 | 抗干扰强 |
| 速率 | 经典 CAN 常见 250k / 500k / 1M | 双方必须一致 |
| 终端电阻 | 总线两端各 120Ω | 缺失导致偶发错误帧 |
| 拓扑 | 线型，节点并联 | 星型分支会引入反射 |

**用万用表量 CAN_H–CAN_L 静态约 2.5V；断总线后量两端电阻约 60Ω（两个 120Ω 并联）。** 这是现场最快的物理层判断。

### 2.2 经典 CAN 帧结构

```
SOF | 仲裁段(ID) | 控制段 | 数据(0..8字节) | CRC | ACK | EOF
```

- 标准帧 11 位 ID，扩展帧 29 位 ID；
- 数据长度最多 8 字节（CAN FD 可到 64）；
- **ID 越小优先级越高**，冲突时非破坏性仲裁，小 ID 赢；
- 每 5 个相同位插入一个反相位（位填充）。

### 2.3 一个可读的帧

```
candump can0
  can0  181   [8]  00 10 20 30 40 50 60 70
```

| 部分 | 含义 |
|---|---|
| `can0` | 接口名 |
| `181` | 十六进制 ID（0x181 = 385） |
| `[8]` | 数据长度 |
| 后面 8 个字节 | 载荷 |

**先看 ID 能不能对上协议表，再看 DLC，最后看字节。** 顺序反了会陷进无意义的数值里。

### 2.4 常见错误状态

| 状态 | 含义 | 处理 |
|---|---|---|
| Error Active | 正常 | — |
| Error Passive | 错误计数高 | 查线束/终端电阻 |
| Bus Off | 节点被踢出总线 | 查短路、波特率、大量错误帧 |

`ip -details link show can0` 能看到 `state` 与 `berr-counter`。

## 3. 可复制命令 / 代码

```bash
ip -details link show can0
candump can0
candump -L can0 > /tmp/can.log     # 带时间戳保存
canbusload can0@500000             # 总线负载（需 can-utils）
```

## 4. 动手实验

**目标（30 分钟）**：手工解析三帧并写结论。

1. 用 `candump -L` 录一段（没有实车可用 S4-02 的 vcan）；
2. 挑三条 ID 不同的帧，按 2.3 的格式拆开；
3. 对照你自己的协议表，写出每帧的「发送方 / 含义 / 数值」；
4. 用 `canbusload` 测 10 秒平均负载；
5. 结论里必须包含：**ID、DLC、字段、物理量、单位**。

**通过判据**：三条帧全部能对应到协议表中的具体信号，不能只写「数据正常」。

## 5. 自动检查

本节无自动实验（需要真实 CAN 接口或 vcan 权限）。自查：

- [ ] 能说出标准帧与扩展帧的 ID 位数；
- [ ] 能解释为什么 ID 小的帧优先；
- [ ] 知道终端电阻为什么是 120Ω 且两端各一个；
- [ ] 能区分 Error Passive 与 Bus Off。

## 6. 常见故障

| 症状 | 原因 | 处理 |
|---|---|---|
| 完全收不到帧 | 波特率不一致 / 未 up | `ip link set can0 up type can bitrate 500000` |
| 偶发错误帧 | 终端电阻缺失/线束分支 | 量 60Ω、改线型拓扑 |
| Bus Off 反复 | 短路或波特率错 | 断开节点逐个排查 |
| 帧有但数值离谱 | 字节序/缩放因子 | 回看 S4-05 |
| 负载 >70% | 周期太短/帧太多 | 降频、合并信号 |
