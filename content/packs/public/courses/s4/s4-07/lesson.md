# S4-07 · 时间同步与驱动封装

> 验证状态：⚠ 本机未做多机 NTP/PTP 同步测试；本课命令为标准 Linux 时间工具，**未实测**。

## 1. 现场类比

两路数据时间戳差 50ms，融合结果就会把「上一秒的位姿」和「这一秒的障碍」拼在一起。

远控+多传感器系统里，**时间不同步是最难查的故障之一**：不报错、不丢帧，只是结果「差一点」。

## 2. 核心概念

### 2.1 两种时钟

| 时钟 | 是否会跳变 | 用途 |
|---|---|---|
| 墙上时钟 `CLOCK_REALTIME` | 会（NTP 校时会跳） | 日志、跨机对齐 |
| 单调时钟 `CLOCK_MONOTONIC` | 不会跳 | 测间隔、控制周期 |

**控制环永远用单调时钟测周期**；跨设备对齐才用墙上时钟。

### 2.2 NTP 与 PTP

| 项目 | NTP | PTP (IEEE 1588) |
|---|---|---|
| 精度 | ms 级 | µs 级 |
| 依赖 | 普通以太网 | 硬件时间戳支持 |
| 现场 | 日志对齐够用 | 多传感器融合需要 |

没有硬件时间戳的网卡做 PTP，精度会退化到接近 NTP。**买设备前先确认网卡是否支持硬件打戳。**

### 2.3 时间戳该在哪一层打

```
采集(硬件) → 驱动 → 中间件 → 算法
   ↑ 最佳        ↑ 次优      ↑ 误差最大
```

**能在驱动或硬件打戳，就不要在算法里补时间戳**——那只是「处理时间」，不是「采样时间」。

### 2.4 驱动封装的四个义务

| 义务 | 说明 |
|---|---|
| 数据转换 | 原始帧 → 物理量（缩放、符号、单位） |
| 时间戳 | 使用采样时刻，不用发布时刻 |
| 健康上报 | 断线、错误计数、超时要有话题 |
| 参数校验 | 非法配置在启动时报错并拒绝启动 |

一个合格的驱动应该是：**拔掉线，上层能立刻知道**，而不是继续发布旧值。

## 4. 动手实验

**目标（35 分钟）**：为你的驱动写一份「健康上报」规范。

1. 列出驱动当前的所有输出话题与频率；
2. 为每个话题注明时间戳来源（硬件/驱动/上层）；
3. 设计一个 `/driver_status` 话题，字段至少包含：连接状态、最近帧时间、错误计数、超时次数；
4. 规定断线时的行为：停止发布数据、置无效、还是保持最后值并报警？（**必须明确**）
5. 写一个「拔线测试」用例，描述预期现象。

**通过判据**：断线时上层能在 1 秒内通过 `/driver_status` 判断出来，且不会把旧值当新值用。

## 5. 自动检查

```bash
python3 -c "import time; a=time.monotonic(); b=time.monotonic(); print(b>a)"
date -u +%Y-%m-%dT%H:%M:%SZ
```

预期输出 `True` 与 UTC 时间。

## 6. 常见故障

| 症状 | 原因 | 处理 |
|---|---|---|
| 多机数据对不上 | 未同步时钟 | NTP/PTP |
| 融合结果飘 | 时间戳用处理时刻 | 在驱动层打戳 |
| 校时后控制周期异常 | 用墙上时钟测间隔 | 改单调时钟 |
| 拔线后仍收到数据 | 驱动缓存旧值 | 超时置无效并上报 |
| 参数改错启动失败无提示 | 缺校验 | 启动时校验并报错退出 |
