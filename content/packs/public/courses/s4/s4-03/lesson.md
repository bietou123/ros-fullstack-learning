# S4-03 · CANopen 基础

## 1. 现场类比

CAN 只规定了「怎么发一帧」，没规定「帧里 8 个字节是什么意思」。各家驱动器自己定，就变成每个设备一套私有协议。

CANopen 是**上层约定**：每个设备有一个对象字典，用标准方式读写；周期数据用 PDO，参数配置用 SDO，网络管理用 NMT。伺服驱动器、比例阀控制器大量采用。

## 2. 核心概念

### 2.1 四类报文

| 报文 | 全称 | 用途 | 典型 COB-ID |
|---|---|---|---|
| NMT | Network Management | 启动/停止/复位节点 | 0x000 |
| SYNC | 同步 | 触发同步 PDO | 0x080 |
| SDO | Service Data Object | 读写对象字典（配置） | 0x600+node / 0x580+node |
| PDO | Process Data Object | 周期传输实时数据 | 0x180+node / 0x200+node |
| EMCY | Emergency | 故障上报 | 0x080+node |

（COB-ID 是默认值，可在字典中修改。）

### 2.2 对象字典

每个对象用 **索引（16 位）+ 子索引（8 位）** 定位，例如 `0x6040:00` 是控制字。

常见对象：

| 索引 | 含义 |
|---|---|
| 0x6040 | 控制字 Controlword |
| 0x6041 | 状态字 Statusword |
| 0x6060 | 运行模式 |
| 0x6064 | 实际位置 |
| 0x607A | 目标位置 |

**控制字/状态字是位域**，每一位对应一个功能，错一位就是完全不同的命令。

### 2.3 SDO 与 PDO 的分工

| 项目 | SDO | PDO |
|---|---|---|
| 用途 | 配置参数（偶发） | 实时数据（周期） |
| 是否确认 | 是（有应答） | 否 |
| 数据量 | 可分多帧 | 一帧内 |
| 现场注意 | 启动时配置，不要周期性用 | 映射关系必须双方一致 |

**最常见的误区**：用 SDO 周期性发控制指令。SDO 有握手，延迟大且会挤占带宽。

### 2.4 NMT 与心跳

- NMT 主站发命令，节点按 node-id 响应；
- 心跳（Heartbeat）周期上报节点状态，主站用它判断掉线；
- **心跳丢了要停输出**，这是 S0-08 看门狗在 CAN 层的具体实现。

## 3. 可复制命令 / 代码

```bash
# 观察（需要设备在线）
candump can0,600~7FF:7FF
candump can0,180~7FF:7FF

# Python 库（canopen）示例骨架
python3 - <<'PY'
import canopen
net = canopen.Network()
net.connect(channel="can0", bustype="socketcan")
node = net.add_node(1, "path/to/device.eds")
print(node.nmt.state)
print(node.sdo[0x6041].raw)
PY
```

`device.eds` 是设备电子数据表——**没有 EDS，靠猜索引是在赌**。

## 4. 动手实验

**目标（40 分钟）**：画出自己的设备通信表。

1. 找一台现场用的 CANopen 设备，拿到它的 EDS；

3. 标注哪些对象是控制字位域，逐位写出含义；
4. 写出心跳周期、超时阈值、掉线后的行为；

## 6. 常见故障

| 症状 | 原因 | 处理 |
|---|---|---|
| 设备不响应 | NMT 未进入 Operational | 发 NMT Start |
| SDO 超时 | 节点 ID/索引错、设备离线 | 核对 ID 与字典 |
| PDO 数值不对 | 映射字节序/缩放不一致 | 用 EDS 核对映射 |
| 周期性 SDO 导致抖动 | 用了阻塞式读写 | 改 PDO |
| 掉线无人知 | 没启用心跳监控 | 中心节点监控 + 看门狗 |
