# S10-05 · 部署与故障演练

> 验证状态：✅ 2026-11-04 本机 Linux 实测重启风暴（crashloop）判定逻辑；⚠ 本机 Docker 引擎可用但未安装 compose 插件，Compose 示例为静态说明，`docker compose up` **未实测**。

## 1. 现场类比

演示前服务起来过一次，就默认「部署完成」。结果现场断电重启后顺序错乱、日志写满磁盘、配置被环境变量覆盖——**能跑一次，不等于能长期运行。**

部署的完成标准不是「起来了」，是「坏了能自动恢复，恢复不了能退回」。

## 2. 核心概念

### 2.1 部署产物清单

| 产物 | 内容 |
|---|---|
| 程序 | 镜像 / 二进制，版本固定 |
| 编排 | Compose / systemd unit |
| 配置 | 配置文件 + 环境变量说明 |
| 标定 | 标定文件与版本 |
| 启动脚本 | 一键启动、健康检查 |
| 回滚包 | 上一版本 + 切换脚本（S8-06） |

### 2.2 Compose 的关键字段

```yaml
services:
  app:
    image: example/app:1.0
    restart: unless-stopped
    healthcheck:
      test: ["CMD", "true"]
      interval: 10s
      retries: 3
    depends_on:
      db:
        condition: service_healthy
    logging:
      driver: json-file
      options: { max-size: "10m", max-file: "3" }
```

要点：

- `depends_on` 要配 `condition: service_healthy`，**不是「容器已启动」**；
- 重启策略要明确，`unless-stopped` 适合常驻服务；
- 日志必须限大小，防止写满磁盘（S8-04）；
- 凭据通过受控方式注入，**不写进 compose 文件**。

### 2.3 健康检查与就绪

| 检查 | 含义 |
|---|---|
| liveness | 进程还活着吗 |
| readiness | 现在能接请求吗 |
| startup | 启动完成了吗 |

只有「活着」不够：启动中的服务活着但不可用，流量打进去就会失败。

### 2.4 崩溃循环（crashloop）

短时间内反复启动失败，重启策略会不断重试：

- 烧 CPU、刷日志、掩盖真正的错误；
- 应设置「连续失败 N 次后停止并告警」；
- 典型原因：配置错误、依赖未就绪、端口冲突、权限不足。

### 2.5 故障演练清单

| 故障 | 注入方式 | 期望行为 |
|---|---|---|
| 进程被杀 | kill | 自动重启或进入安全态 |
| 依赖不可用 | 停数据库 | 启动等待，不进入 crashloop |
| 网络中断 | 断开链路 | 控制链路进入安全状态（S6-05） |
| 磁盘写满 | 填充测试文件 | 告警并停止写入，不崩溃 |
| 配置错误 | 注入非法值 | fail fast，拒绝启动 |
| 时钟偏移 | 改时间 | 检测并告警（S4-07） |
| 传感器丢失 | 停数据源 | 进入降级或故障态 |

**每项都要记录：检测时间、动作、恢复时间、是否自动。**

### 2.6 演练记录模板

```
故障类型 | 注入方法 | 检测方式 | 系统动作 | 恢复耗时 | 是否自动 | 遗留问题
```

没有记录的演练，等于没演练。

### 2.7 回滚也要演练

部署演练必须包含一次「升级失败 → 切回旧版本」，并记录耗时（S8-06）。

## 3. 可复制命令 / 代码

```bash
# 重启风暴判定：60 秒窗口内失败次数
python3 -c "events=[0,5,12,40,55,70]; window=60; limit=3; mx=max(sum(1 for t in events if s<=t<s+window) for s in events); print('fails=%d max_in_60s=%d crashloop=%s'%(len(events),mx,mx>=limit))"
```

预期：

```
fails=6 max_in_60s=5 crashloop=True
```

含义：60 秒窗口内最多 5 次失败，超过阈值 3，判定为崩溃循环，应停止重启并告警。

## 4. 动手实验

**目标（45 分钟）**：完成一次部署 + 故障演练。

1. 写出部署产物清单，标注每项版本；
2. 为服务配置健康检查与依赖就绪条件；
3. 按 2.5 的清单至少演练 3 类故障；
4. 用第 3 节代码判断是否出现重启风暴；
5. 执行一次回滚，记录耗时；
6. 填写演练记录表；
7. 写结论：哪类故障恢复最慢？哪项仍是手动的？

**通过判据**：至少 3 类故障有记录；重启风暴能被识别；回滚在目标时间内完成。

## 5. 自动检查

```bash
python3 -c "events=[0,5,12,40,55,70]; window=60; limit=3; mx=max(sum(1 for t in events if s<=t<s+window) for s in events); assert mx==5 and mx>=limit; print('DRILL_OK')"
```

预期输出 `DRILL_OK`。

## 6. 常见故障

| 症状 | 可能原因 | 排查 |
|---|---|---|
| 容器起来但服务不可用 | 只检查「已启动」 | 加 readiness / healthcheck |
| 反复重启刷爆日志 | 无失败阈值 | 限制重试，停止并告警 |
| 重启后依赖没就绪 | `depends_on` 未配健康条件 | 等依赖 healthy 再启动 |
| 磁盘被日志写满 | 无日志轮转 | 配置 max-size（S8-04） |
| 配置错但服务照常起 | 未 fail fast | 启动校验，非法值直接退出 |
| 断网后设备保持动作 | 无超时保护 | 看门狗 + 安全态（S6-05） |
| 升级失败回不去 | 未保留旧版本 | 版本目录 + 软链（S8-06） |
