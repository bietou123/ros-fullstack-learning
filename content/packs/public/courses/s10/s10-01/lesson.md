# S10-01 · 项目拆解与验收标准

> 验证状态：✅ 本机 Linux 实测了 WBS 工作量与依赖顺序校验；⚠ 本项目为**纯软件虚拟远控台**，不连接任何真实设备，尺寸与参数均为教学示例值。

## 1. 现场类比

接到一个「把远控做出来」的任务，两周后交。第一反应是打开编辑器写代码——写到第三天发现执行器模型还没定、验收标准没人说得清、标定数据格式和状态机对不上。

**项目不是「一直写」，是先把不确定的东西拆开、排好顺序、定义什么叫完成。**

## 2. 核心概念

### 2.1 毕业项目范围

本课程的项目是一个**虚拟远控台**，全部在 PC / 容器内运行：

| 模块 | 内容 | 对应课程 |
|---|---|---|
| 执行器模型 | 虚拟 CAN + 一阶响应 + 饱和 | S10-02 |
| 指令链路 | 座舱指令 + 安全状态机 | S10-03 |
| 标定与 TF | 传感器到机体的坐标链 | S10-04 |
| 部署 | Compose + 故障演练 | S10-05 |
| 验收 | 报告与答辩 | S10-06 |

**不接入真实设备，不使用现场参数，不包含任何客户信息。**

### 2.2 工作分解（WBS）

每个工作包必须写清：

1. 交付物是什么；
2. 预估工作量（人日）；
3. 依赖哪些前置包；
4. 验收标准是什么。

只写「做控制」不是工作包，**「实现阶跃响应 t90 ≤ 0.3 s 的执行器模型并附带测试」才是。**

### 2.3 依赖与顺序

```
A 需求与验收标准
 ├→ B 执行器模型 ─┐
 └→ C 指令与状态机 ┼→ E 部署与演练 → F 验收报告
        D 标定与TF ─┘
```

依赖关系决定顺序。**先做被依赖的、风险高的；把「能不能做」的问题放在前面。**

### 2.4 验收标准（Definition of Done）

| 工作包 | 可测判据（示例） |
|---|---|
| 执行器模型 | 阶跃响应 t90 在设定范围内；超限指令被饱和 |
| 指令状态机 | 非法转换被拒绝；超时进入故障态 |
| 标定与 TF | 正向变换结果与手算一致，误差在阈值内 |
| 部署 | 一条命令起服务；故障后自动重启或进入安全态 |
| 报告 | 每个结论都有数据或日志支撑 |

**「做完了」= 判据通过 + 有证据，不是「我觉得可以了」。**

### 2.5 里程碑

| 里程碑 | 完成标志 |
|---|---|
| M1 | WBS、依赖、验收标准冻结 |
| M2 | 执行器 + 状态机可独立运行 |
| M3 | 标定/TF 集成，端到端链路通 |
| M4 | 部署 + 故障演练通过 |
| M5 | 报告完成，答辩通过 |

### 2.6 范围控制

明确写出**不做什么**：

- 不接真实设备、不做实时性硬指标验证；
- 不实现完整 SLAM/导航；
- 不做 UI 美化；
- 不引入额外框架。

范围一旦冻结，新增需求进入「后续版本」，不插队。

### 2.7 风险登记

前 3 项风险，每项写触发条件、影响、应对。项目早期就要写，不是最后补。

## 3. 可复制命令 / 代码

```bash
# WBS：工作包数量、总工作量、最终交付物
python3 -c "wp=[('A','需求与验收标准',2,['-']),('B','执行器模型',3,['A']),('C','指令与状态机',4,['A']),('D','标定与TF',3,['B']),('E','部署与演练',2,['C','D']),('F','验收报告',2,['E'])]; total=sum(w for _,_,w,_ in wp); print('wp=%d person_days=%d final=%s'%(len(wp),total,wp[-1][0]))"
```

预期：

```
wp=6 person_days=16 final=F
```

## 4. 动手实验

**目标（30 分钟）**：产出一份可执行的毕业项目 WBS。

1. 按 2.1 的模块拆出 5–8 个工作包；
2. 每个包写交付物、人日、依赖、验收判据；
3. 检查依赖顺序没有环、没有「依赖自己」；
4. 用第 3 节代码校验总量与最终包；
5. 写出「不做什么」清单；
6. 登记前 3 项风险与应对。

**通过判据**：每个工作包都有可测判据；依赖顺序合法；范围与风险写清楚。

## 5. 自动检查

```bash
python3 -c "wp=[('A','需求与验收标准',2,['-']),('B','执行器模型',3,['A']),('C','指令与状态机',4,['A']),('D','标定与TF',3,['B']),('E','部署与演练',2,['C','D']),('F','验收报告',2,['E'])]; ids={w[0]:i for i,w in enumerate(wp)}; bad=[(w[0],d) for w in wp for d in w[3] if d not in ('-','—') and ids[d]>=ids[w[0]]]; assert not bad and sum(w for _,_,w,_ in wp)==16; print('WBS_OK')"
```

预期输出 `WBS_OK`。

## 6. 常见故障

| 症状 | 可能原因 | 排查 |
|---|---|---|
| 快交付了还在改需求 | 范围未冻结 | 新增进后续版本，不插队 |
| 两个模块接口对不上 | 验收标准未定义 | 先冻结接口与数据格式 |
| 总做「简单但不重要」的 | 未按依赖与风险排序 | 先做被依赖、风险高的包 |
| 进度估算总是偏乐观 | 人日没有拆细 | 按 0.5–2 人日粒度拆 |
| 验收时各说各话 | 判据模糊 | 改成数值或明确状态 |
| 最后才发现做不完 | 无里程碑检查 | 每个里程碑做一次范围复核 |
