# S9-04 · 演示脚本编写

> 验证状态：✅ 本机 Linux 实测了演示脚本的分段时长校验；⚠ 未进行真实展会/客户现场彩排，时间预算为教学示例值。

## 1. 现场类比

五分钟演示，前三分钟在调连接，最后两分钟手忙脚乱做动作。观众记住的不是功能，是「卡了」。

**演示不是即兴发挥，是一条被排练过、带兜底方案的脚本。**

## 2. 核心概念

### 2.1 五分钟要证明什么

| 目标 | 观众想看到的 |
|---|---|
| 能力 | 设备真的能完成有意义的动作 |
| 安全 | 出问题时能停下来 |
| 可靠 | 同样的操作能重复成功 |

不是把所有功能演一遍，而是**用最少的动作证明这三件事**。

### 2.2 脚本分段（教学示例）

| 片段 | 时长 | 目的 |
|---|---:|---|
| 开场 | 30 s | 一句话说明价值，告诉观众接下来看什么 |
| 连接与就绪 | 40 s | 展示正常启动流程（S8-07） |
| 基础动作 | 90 s | 核心能力，成功率高 |
| 精度 / 组合动作 | 60 s | 体现控制水平 |
| 安全演示 | 50 s | 急停 / 超时保护（S6-04、S6-05） |
| 收尾与问答 | 30 s | 一句总结，留下资料 |

合计 300 s。**总时长不超过可用时间的 80%**，留出切换与意外。

### 2.3 每个片段写四件事

1. 目的：这一段要证明什么；
2. 操作：谁按什么、按几下；
3. 预期画面：观众应该看到什么；
4. 失败兜底：这一步失败时切到哪里。

**没有兜底的片段，就是演示的风险点。**

### 2.4 兜底方案（Plan B）

- 连接失败 → 切备用链路或备用设备；
- 动作失败 → 停止、说明、切预录素材（若现场允许）；
- 传感器异常 → 展示故障检测与安全停机，把事故变成安全能力的证明；
- 时间超支 → 跳过精度段，保安全段与收尾。

**兜底要提前演练，不是现场现想。**

### 2.5 排练纪律

- 全流程至少 3 次，每次计时；
- 记录卡点与超时段；
- 换一个人操作一次——演示者不一定是开发者；
- 在接近现场的环境下排练（灯光、噪声、网络）。

### 2.6 讲解词

每段 1–2 句，说清「是什么、为什么重要」，**不要念参数**。参数留给问答。

### 2.7 收尾

一句总结 + 一句后续（资料、联系方式、下一步计划）。收尾仓促会让整场演示显得没准备。

## 3. 可复制命令 / 代码

```bash
# 校验演示脚本时长：总时长与单段上限
python3 -c "seg=[('intro',30),('connect',40),('basic_move',90),('precision',60),('safety_stop',50),('qa',30)]; total=sum(s for _,s in seg); print('total_s=%d segments=%d max_seg=%d'%(total,len(seg),max(s for _,s in seg)))"
```

预期：

```
total_s=300 segments=6 max_seg=90
```

## 4. 动手实验

**目标（30 分钟）**：写出一份可执行的五分钟演示脚本，并计时排练一次。

1. 按 2.2 的结构写出 5–6 个片段，每段填四件事；
2. 用第 3 节代码校验总时长与单段上限；
3. 为每个高风险片段写兜底动作；
4. 完整排练一次并计时，记录实际与计划的偏差；
5. 人为制造一次连接失败，执行兜底方案；
6. 写结论：哪一段最容易超时？兜底是否真的可用？

**通过判据**：脚本总时长在预算内；每个片段有兜底；实际排练能走完且偏差可解释。

## 6. 常见故障

| 症状 | 可能原因 | 排查 |
|---|---|---|
| 演示总超时 | 片段过多、无时间预算 | 砍功能，保核心与安全段 |
| 开场就在调设备 | 没有就绪检查 | 提前按 S8-07 走开机流程 |
| 动作失败后冷场 | 无兜底方案 | 每段写 Plan B 并演练 |
| 讲解变成念参数 | 讲解词没准备 | 每段只留 1–2 句结论 |
| 换人操作就出错 | 只排练了固定操作者 | 换人排练一次 |
| 现场灯光/噪声影响识别 | 未在近似环境排练 | 提前到场适配 |
| 收尾仓促 | 前面超时挤压 | 预留 20% 时间冗余 |
