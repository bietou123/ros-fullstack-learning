# S9-02 · Edge Bridge 配置优先级

> 验证状态：✅ 本机 Linux 实测了分层配置合并与优先级验证；⚠ 配置项名称与默认值为**教学示例**，与现场实际组件配置无关。

## 1. 现场类比

现场把配置文件里的频率从 10 改成 20，重启后还是 10。查了半小时才发现：环境变量里有个旧值把它覆盖了。

**参数不生效，往往不是「没改」，而是「改了但被更高优先级盖住了」。**

## 2. 核心概念

### 2.1 为什么要分层

| 层 | 来源 | 典型用途 |
|---|---|---|
| 默认值 | 程序内置 | 出厂可用 |
| 配置文件 | 部署目录 | 现场适配 |
| 环境变量 | 进程环境 | 容器 / 临时覆盖 |
| 命令行参数 | 启动命令 | 排障、单次实验 |

### 2.2 优先级必须写死

常见顺序（低 → 高）：

```
默认值 < 配置文件 < 环境变量 < 命令行参数
```

**规则本身不重要，重要的是明确、稳定、可查询。** 同一套系统里不同组件各用一套顺序，排障时会互相误导。

### 2.3 合并规则的两个陷阱

1. **对象是深度合并，数组通常是整体替换**——配置文件写 `topics: [a, b]`，环境变量写 `topics: [c]`，结果可能是 `[c]` 而不是 `[a, b, c]`；
2. **空值语义**：`null` 是「清除」还是「忽略」，必须在文档里写死。

### 2.4 生效配置必须可打印

启动时输出最终生效值与**来源**：

```
rate=20 (source=env)
mode=safe (source=env)
topic=/cmd_remote (source=cli)
```

没有来源信息，排障只能靠猜。**能打印生效配置，是配置系统的最低要求。**

### 2.5 校验要 fail fast

类型错误、超出范围、互斥项同时开启——启动时直接失败并给出明确错误，**不要静默回退默认值**。静默回退会让「看起来正常」掩盖真正的问题。

### 2.6 环境变量的命名约定

- 统一前缀，避免与其他程序冲突；
- 用双下划线表达层级，例如 `APP__NETWORK__RATE`；
- 大小写规则写进文档，不要依赖平台默认行为（Linux 大小写敏感，Windows 不敏感）。

### 2.7 现场排查顺序

1. 打印生效配置与来源；
2. 找到赢家所在层；
3. 从高到低逐层删除，确认每一层的实际值；
4. 修正后重启，再打印一次确认。

## 3. 可复制命令 / 代码

```bash
# 四层配置合并：默认 < 文件 < 环境 < 命令行
python3 -c "base={'rate':10,'topic':'/cmd','mode':'normal'}; file={'rate':20}; env={'mode':'safe'}; cli={'topic':'/cmd_remote'}; cfg={**base,**file,**env,**cli}; print(cfg)"
```

预期：

```
{'rate': 20, 'topic': '/cmd_remote', 'mode': 'safe'}
```

逐项看：`rate` 来自配置文件，`mode` 来自环境变量，`topic` 来自命令行——**后合并的层覆盖前面的层。**

## 4. 动手实验

**目标（35 分钟）**：复现一次「改了不生效」，并用优先级模型定位。

1. 定义四个配置层与至少三个参数；
2. 在多层给同一参数设置不同值，运行合并脚本；
3. 记录最终值，并注明每个值的来源层；
4. 人为制造一个冲突（例如环境变量覆盖配置文件），确认脚本行为符合预期；
5. 验证数组参数是替换还是合并；
6. 写结论：优先级顺序、数组规则、排障时第一步看什么。

**通过判据**：能准确说出每个参数最终值来自哪一层；能解释一次「改了不生效」的具体原因。

## 5. 自动检查

```bash
python3 -c "base={'rate':10,'topic':'/cmd','mode':'normal'}; file={'rate':20}; env={'mode':'safe'}; cli={'topic':'/cmd_remote'}; cfg={**base,**file,**env,**cli}; assert cfg['rate']==20 and cfg['topic']=='/cmd_remote' and cfg['mode']=='safe'; print('CONFIG_OK')"
```

预期输出 `CONFIG_OK`。

## 6. 常见故障

| 症状 | 可能原因 | 排查 |
|---|---|---|
| 改了配置不生效 | 被更高优先级覆盖 | 打印生效值与来源 |
| 两个环境值互相打架 | 多层都设置了同一项 | 逐层删除定位 |
| 数组配置变少 | 高层整体替换了数组 | 查合并规则，必要时合并后再赋值 |
| 容器内外行为不同 | 环境变量未传入容器 | 检查启动参数与 env 注入 |
| 本地正常、现场异常 | 现场配置层有旧值 | 对比两层配置差异 |
| 参数类型错误但没报错 | 静默回退默认值 | 改为 fail fast + 启动校验 |
| 大小写不一致导致不生效 | Linux/Windows 行为差异 | 统一命名规范 |
