# S6-05 · 看门狗与心跳

> 验证状态：✅ 本课心跳超时检测命令已在本机 Linux 实测（合成时间戳）；⚠ 未与实机控制循环联调，超时参数为**教学示例**。

## 1. 现场类比

控制电脑卡死了，驱动板还在按最后一帧指令输出。屏幕不动，机器不停。

**没有心跳，上层就不知道下层是不是还活着。** 看门狗的任务不是「发现问题」，而是「发现后让系统进入安全状态」。

## 2. 核心概念

### 2.1 四个参数必须写死

| 参数 | 含义 | 示例（教学值） |
|---|---|---|
| 心跳周期 | 多久发一次 | 20 ms |
| 超时阈值 | 多久没收到算失联 | 100 ms（约 5 个周期） |
| 检测对象 | 检测谁 | 控制循环 / 远程操作端 / 驱动器 |
| 超时行为 | 失联后做什么 | 输出归零 + 进入 Fault + 上报 |

**四个参数少一个，看门狗就等于没设计。**

### 2.2 喂狗的位置决定它有没有用

| 喂狗位置 | 能发现什么 | 发现不了什么 |
|---|---|---|
| 独立线程定时喂 | 进程崩溃 | 控制循环卡死 |
| 控制循环开头喂 | 上一轮卡死 | 本轮卡死 |
| **控制循环完成一轮后喂** | 循环整体卡死 | —— |
| 由别的进程代喂 | 几乎没有 | 几乎全部 |

**喂狗必须放在「真正完成工作」之后**，否则只是证明「定时器还活着」。

### 2.3 超时阈值怎么定

```
超时阈值 ≥ 3 × 心跳周期 + 系统最大抖动
```

太短：正常调度抖动就误触发；太长：失联后反应慢。阈值必须实测抖动后确定，不能凭感觉。

### 2.4 超时行为与恢复

```
正常 ──心跳丢失超过阈值──▶ 安全停机（输出归零/断使能）
                                  │
                                  ├─ 上报：失联对象、最后心跳时间
                                  └─ 恢复：必须显式确认，不能自动回到运行
```

自动恢复听起来方便，但**故障原因没查明就自动恢复**，可能反复动作，风险更高。

## 3. 可复制命令 / 代码

```bash
# 心跳时间戳中最大间隔 0.20 s，超过 0.15 s 阈值 → 判定失联
python3 -c "hb=[0.0,0.05,0.10,0.30,0.35,0.40]; gaps=[b-a for a,b in zip(hb,hb[1:])]; print('max_gap=%.2f timeout=%s'%(max(gaps),max(gaps)>0.15))"
```

预期：`max_gap=0.20 timeout=True`。丢失的帧被间隔暴露出来，不需要逐帧检查。

## 4. 动手实验

**目标（35 分钟）**：为你的控制链路设计一套看门狗，并测出最坏反应时间。

1. 选一个被监控对象（控制循环、远程端、驱动器）；
2. 定义心跳周期、超时阈值、超时行为、恢复方式；
3. 说明喂狗位置，并解释为什么放在那里；
4. 用本课代码模拟丢 1 帧、丢 3 帧、彻底失联三种情况；
5. 计算从失联到进入安全状态的最坏时间（阈值 + 处理时间）；
6. 写结论：最坏反应时间是否满足安全要求？误触发风险如何？

**通过判据**：四个参数齐全、喂狗位置有理由、最坏反应时间可计算，且恢复必须显式确认。

## 6. 常见故障

| 症状 | 可能原因 | 排查 |
|---|---|---|
| 频繁误停机 | 阈值太紧、系统抖动大 | 实测抖动，放宽到 3–5 个周期 |
| 卡死后仍在动 | 喂狗在独立线程/由别的进程代喂 | 把喂狗移到控制循环末尾 |
| 失联很久才发现 | 阈值过大、心跳周期过长 | 缩短周期与阈值 |
| 恢复后直接高速运行 | 恢复逻辑跳过了使能流程 | 恢复只回 Idle |
| 心跳正常但数据不动 | 心跳与数据不同源 | 心跳要绑定真实工作完成 |
| 网络抖动导致误判 | 未区分单次丢帧与持续失联 | 用连续 N 次超时判定 |
| 日志看不出失联对象 | 上报字段不全 | 记录对象、最后时间、超时次数 |
