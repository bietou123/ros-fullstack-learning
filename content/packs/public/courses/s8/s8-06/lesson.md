# S8-06 · 远程升级与回滚

> 验证状态：✅ 本机 Linux 实测了基于版本目录 + 软链切换的升级与回滚流程；⚠ 未在真实设备上演练完整升级包、服务重启与断电恢复。

## 1. 现场类比

现场升级到一半断电，设备起不来。工程师从办公室赶来，用 U 盘重装系统，折腾两小时——**这两小时里设备停着，产线也停着。**

好的升级方案不是「保证不出错」，而是「出错后十分钟内退回上一版」。

## 2. 核心概念

### 2.1 升级的三个层次

| 层次 | 内容 | 回滚难度 |
|---|---|---|
| 固件 | MCU / 驱动 / BIOS | 高，部分需物理操作或双分区 |
| 应用与依赖 | 容器镜像、程序包、配置 | 中，版本目录 + 软链可快速回退 |
| 参数与标定 | 现场标定值、配方 | 低，但要**先备份** |

**不要把三层混成一次「大升级」**：任何一层出问题，都说不清是谁的问题。

### 2.2 版本目录 + 软链

```
/opt/robot/
  releases/
    v1.4.2/     # 完整旧版本
    v1.5.0/     # 完整新版本
  current -> releases/v1.5.0
```

- 升级：把新版本放进 `releases/`，切换 `current` 软链，重启服务；
- 回滚：把 `current` 指回旧目录，重启服务；
- 旧版本目录**保留一段时间**再清理，这是回滚的物质基础。

**只覆盖原地文件，就等于放弃了回滚。**

### 2.3 切换命令的两个细节

```bash
ln -sfn releases/v1.4.2 current   # -n：已存在链接时替换它，而不是放进它指向的目录里
readlink -f current               # 确认当前实际指向
```

漏掉 `-n` 时，`ln` 可能把链接建到**目标目录内部**，现象是 `current/current`，容易看错。

### 2.4 升级前的检查清单

| 项 | 要求 |
|---|---|
| 备份 | 配置、标定、数据库先备份并校验可读 |
| 磁盘 | 新区间 + 旧版本 + 备份后仍有 ≥ 20% 余量 |
| 版本兼容 | 应用 / 驱动 / 配置格式兼容，或提供迁移脚本 |
| 升级窗口 | 与现场约好停机时间，有人在场 |
| 回滚路径 | **事先演练过**，不是写在文档里没跑过 |
| 回滚判据 | 明确触发条件，见 2.5 |

### 2.5 回滚判据要写死

不要靠「感觉不对就回滚」。用可测量条件：

- 服务连续启动失败 ≥ 2 次；
- 关键话题 30 s 内缺失；
- 端到端延迟 P95 超过阈值并持续 1 min；
- 安全功能（急停、看门狗）自检不通过——**立即回滚，不讨论**。

**判据写死，现场才敢做决定。**

### 2.6 常见升级策略

| 策略 | 说明 | 风险 |
|---|---|---|
| 直接替换 + 软链 | 单机最常用 | 升级期间服务中断 |
| A/B 双分区 | 嵌入式常见，可重启切换 | 分区与镜像管理复杂 |
| 灰度 / 分批 | 先一台验证再推广 | 需要版本管理与回传统一 |
| 容器滚动 | 多实例平滑切换 | 依赖编排平台 |

镜像 tag 固定到具体版本，**不用 `latest`**——否则「回滚」到的是另一个不明版本。

### 2.7 数据迁移的单向陷阱

数据库 schema 迁移通常**只能前进不能后退**：新版本升级了表结构，回滚旧程序会读不懂。

对策：迁移前完整备份；迁移脚本与回滚脚本成对提供；大版本升级先在副本上演练。

## 3. 可复制命令 / 代码

```bash
# 版本目录 + 软链：升级、回滚演练
d=$(mktemp -d)
mkdir -p $d/releases/v1 $d/releases/v2
ln -s releases/v1 $d/current
echo "running=$(basename $(readlink -f $d/current))"
ln -sfn releases/v2 $d/current
echo "after_upgrade=$(basename $(readlink -f $d/current))"
ln -sfn releases/v1 $d/current
echo "after_rollback=$(basename $(readlink -f $d/current))"
rm -rf $d
```

预期：

```
running=v1
after_upgrade=v2
after_rollback=v1
```

真实设备上，切换软链后执行 `systemctl restart <service>`，再按 2.5 的判据验证。

## 4. 动手实验

**目标（35 分钟）**：搭建可回滚的发布目录，记录一次升级与回滚的耗时。

1. 建立 `releases/v1`、`releases/v2` 两个目录，内容可先用占位文件；
2. 用软链 `current` 指向 `v1`，确认 `readlink -f` 输出正确；
3. 模拟升级：切换到 `v2`，记录「从开始到服务可用」的耗时；
4. 模拟故障：人为让 `v2` 启动失败（例如缺少配置文件）；
5. 执行回滚：切回 `v1`，记录从决定回滚到恢复正常的耗时；
6. 写结论：回滚耗时多少？卡在哪一步？判据是否明确？

**通过判据**：能在一分钟内完成一次可验证的回滚；回滚后有明确的验证动作，而不是「看起来好了」。

## 5. 自动检查

```bash
d=$(mktemp -d)
mkdir -p $d/releases/v1 $d/releases/v2
ln -s releases/v1 $d/current
ln -sfn releases/v2 $d/current
up=$(basename $(readlink -f $d/current))
ln -sfn releases/v1 $d/current
rb=$(basename $(readlink -f $d/current))
rm -rf $d
[ "$up" = "v2" ] && [ "$rb" = "v1" ] && echo ROLLBACK_OK
```

预期输出 `ROLLBACK_OK`。

## 6. 常见故障

| 症状 | 可能原因 | 排查 |
|---|---|---|
| 回滚后仍报同样错误 | 配置/数据未一起回滚 | 检查配置目录是否也在版本内 |
| `current/current` 套娃 | `ln` 漏了 `-n` | 用 `ln -sfn` 重建链接 |
| 升级后服务起不来 | 依赖或配置格式不兼容 | 看启动日志，按判据回滚 |
| 回滚成功但数据丢失 | 未备份或迁移不可逆 | 迁移前备份，成对提供回滚脚本 |
| 回滚后空间不够 | 旧版本被提前清理 | 保留 N-1 与 N-2 版本 |
| 升级中断电导致半新半旧 | 原地覆盖、无原子切换 | 改用版本目录 + 软链或 A/B 分区 |
| 同一批设备版本混乱 | 无版本记录 | 部署后写回版本号，集中核对 |
